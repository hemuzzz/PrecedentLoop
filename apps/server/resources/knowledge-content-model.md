# 知识内容模型

MEMORY／DOCUMENT／SKILL 的唯一正文与审阅模板入口。机器字段以 `apps/server/src/asset/schema.ts` 为准；知识的元数据与 Markdown 正文保存在主库，以下章节是内容要求。

## 小型判断档案

知识保存可独立理解的判断及其必要依据。它应回答：结论是什么、什么条件下适用、为什么这样判断、保存的材料支持什么、再次使用须核验哪些决定性前提。修改已有判断时补充变更原因。以上是信息完整性要求，不要求固定章节名或统一篇幅，旧知识不因此强制重写或退出索引。

类型差异：

- MEMORY 围绕一个独立可复用的判断短写，交代处理对象、适用条件和关键边界，避免只留下泛泛口号。
- DOCUMENT 沿用自然章节，条件、用途、来源与验证边界可分布在前言及相关章节；纯资料没有决策过程时，不编造取舍。导航文档可保持导读用途，但不能宣称保存了全部被引用内容。
- SKILL 主干为触发、输入／前置条件、步骤、验证及停止条件；原理和历史案例是支持材料。业务运行方式与 Agent 执行方法分别表达，库内 SKILL 类型不等于客户端已安装。

## 正文模板

ID 使用现有生成器；WORKSPACE 填已配置的 workspace，GLOBAL 省略该字段。`summary` 与正文结论一致，保留决定性的适用前提与历史性限定。以下占位内容仅示范结构，不是可直接确认的知识；不新增机器字段。

````markdown
# <主题>

## 结论与适用条件
<明确结论：规范要求、历史观察或特定时点的实现情况。>
<项目／环境／前提及主要不适用情况；GLOBAL 不代替语义条件。>

## 理由与取舍
<理由与代价，不编造备选方案>

## 依据与验证边界
- 来源与用途：<说明依据是什么、支持哪项判断；链接只是线索>
- 已验证：<实际验证的对象、方式和结果；未运行则注明>
- 未验证：<尚未核实的内容及边界>

## 历史依据（可选）

### 依据 A：<支持的具体判断>

- 材料与时间：<实际来源；材料所述时间／观察时间，未知写未知>
- 留存说明：<当时留存／本次补采；实际留存时间及出处>
- 来源线索：<可选项目、相对路径、符号、章节或链接>
- 材料处理：<原始／分段／脱敏摘录或转写；说明省略和实际变动>

```text
<真实取得且获准保存的必要材料，不补造原文>
```

说明：<支持什么；哪些属于解释或推断>
边界：<未证明什么，依赖哪些未一并保存的上下文>

## 再次使用时的核验点
<决定能否复用的少量条件；哪类工作才需要核对哪些当前事实>
<已经核验且仍适用的证据可复用>

## 当前来源线索（可选）
<用于核对目标环境当前实现，不替换历史依据；位置失效不自动否定知识>

## 本次变更说明（仅修订时）
<改了什么、为什么改变、适用条件变化及未验证项>
````

按需合并章节并删去不适用的占位内容；没有历史摘录时省略整个可选章节，首次新增不附空版本表。示意代码另设“示例／推演”，不能放在原始材料位置。模型推断、Native 线索和摘要不是执行验证证据。

## 历史材料的选择与审核

- 结论、条件和理由已完整，来源仅作补充时，无需复制片段。特定条款、代码分支或实验结果不可替代时，保存足以检查该判断的最小材料；多个局部分别说明作用，不拼成伪连续原文，不用统一行数代替充分性判断。
- 材料不足时缩小断言、说明缺口或等待补充。超过既有大小限制时收窄知识范围，不默删决定性上下文后仍宣称完整，也不以此引入归档平台。
- 分清材料所述的历史时间、实际观察时间和本次留存时间。本次从当前环境取得的材料仅称本次补采，不因路径相同就声称恢复历史；未知日期不从 Asset 创建时间反推。知识版本号用于检测内容变化，不证明材料真实、语义正确或曾被执行。
- 原文、解释、推断和示例分别标注；省略、脱敏、转写与改写说明实际处理。脱敏破坏依据时缩小结论或保持项目专属范围，GLOBAL 通用结论不授权披露项目材料。
- 修订保留当前判断仍依赖的关键历史材料。主库仅保存当前内容与一份 `previous_content` JSON，后续修订会覆盖上一版；明确移除材料时说明可能无法恢复。库内引用不是不可变版本，目标不可读时报告缺口。

### 外部链接遮蔽检查

审核时暂时隐藏外部 URL、路径和行号，检查是否仍能解释核心结论、适用条件与理由；必要背景应已写明，或由当前授权可读的库内知识承载。只剩“见某文件”时须补齐意思，导航 DOCUMENT 则明确导读用途。通过只证明语义相对完整，不证明判断正确，也不要求真的删除链接或读取所有外部来源。

### 旧知识的局部整理

仅在用户选定和授权的范围内整理：正文完整可保持原样；正文有缺口且可靠材料尚存时准备语义补齐与必要摘录；只有当前材料时标明本次补采；仅死链接且无材料时保留已知信息、报告不足。同名或相似片段只是定位线索，不能自动回写。发现敏感、越界或伪原文风险时暂停相关复制或确认，不擅自删除。

批量提议可用简单 Markdown 清单，逐条列出 Asset 身份与基线版本、内容缺口、实际材料及时间、建议处理、确切正文／Diff 和未验证边界。不新增质量状态或账本；结构化候选修订方式由 MCP 工具说明定义，正式确认在 Hub 中逐条进行。

## 候选审阅展示模板

聊天正文按以下格式展示，字段间保留空行；细节留在完整候选中，默认不展示版本号，不加文件 Emoji，不重复播报摘要。

```markdown
**<项目名或 GLOBAL> · 知识候选**

**【标题】** <知识标题>

**【摘要】** <一到两句核心判断及关键前提>

**【原因】** <建议新增／扩展／修订及增量理由>

候选 #<编号>

已在 Precedent Loop 中打开候选页，请审核（接受入库｜修改｜暂存｜拒绝）
```

结构化 MCP 返回的 display 使用本模板，原因仅描述新增或基于正式基线的修订，不虚构比较结果。服务端生成正文、留存时间和相关知识标题；返回候选身份、显示编号与 version，用户在 Hub 审阅完整候选后确认。修订还绑定正式基线版本，内容变化时须重新审阅。

### 反馈入口

本期候选随工程交付展示。能通知 App 时，生成候选的最后一行为“已在 Precedent Loop 中打开候选页，请审核（接受入库｜修改｜暂存｜拒绝）”；不能通知 App 时，模板最后一行保持“请在 Hub 候选管理中审核（接受入库｜修改｜暂存｜拒绝）”。修改候选分别为“已修改候选 #N，已回到待审，已在 Precedent Loop 中打开候选页”或“已修改候选 #N，已回到待审，请在 Hub 候选管理中审核”。聊天内确认工具不在本期范围；未回复、超时或仅有准备成功均不算接受。确认、修改、暂存与拒绝均在 Hub 候选管理完成，授权与版本边界由 MCP 工具说明定义。

修订返回 `REVISION_BLOCKED` 时，本次没有写入，不重试、不拉起 App；把返回的 `display` 原样放在最终回复最后，评估记为 `FAILED` 并写明阻塞候选编号。用户处理候选后，先用 `asset_read` 取最新 `version` 再重新准备修订。同主题补充仍通过 `candidate_update` 合并。

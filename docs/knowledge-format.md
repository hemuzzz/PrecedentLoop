# Knowledge format

Precedents are plain Markdown files with a small front matter block. This page describes the types, scopes, folder layout and file rules.

Most of the time you do not write these files by hand: agents prepare candidates, the Hub imports existing notes, and the app writes approved files for you. This page is useful when you want to read, back up or edit the files directly.

## Types

| Type | Use it for | How recall delivers it |
|---|---|---|
| `MEMORY` | One reusable judgment: a decision, a root cause, a lesson, a pitfall | Summary inline when it matches well; full text on request |
| `SKILL` | A verified, repeatable procedure: trigger, prerequisites, steps, verification, when to stop | As a reference; read on request |
| `DOCUMENT` | Reference material with natural sections | As a reference; read on request |

When in doubt, use `MEMORY`.

## Scopes

- **`WORKSPACE`** — knowledge about one registered project. This is the default.
- **`GLOBAL`** — knowledge that is useful in a completely different project *and* can be stated without this project's name, paths or domain terms.

If a piece of knowledge touches both, split it into a global precedent and a project one.

## Folder layout

```text
repository/
├── assets/                  # approved precedents (searchable)
│   ├── global/
│   │   ├── memories/
│   │   ├── documents/
│   │   └── skills/
│   └── workspaces/
│       └── <project>/
│           ├── memories/
│           ├── documents/
│           └── skills/
└── inbox/                   # candidates waiting for review (never searchable)
    ├── global/…             # same structure as assets/
    └── workspaces/<project>/…
```

Only files under `assets/` are indexed. Accepting a candidate moves it from `inbox/…` to the matching path under `assets/…`.

## File format

```markdown
---
id: ast2034512345678901248
type: MEMORY
scope: WORKSPACE
workspace: example-project
title: Payment callbacks must be idempotent
summary: A repeated callback must never credit the account twice; deduplicate on the provider's transaction ID.
---

# Payment callbacks must be idempotent

Full text…
```

Front matter fields (no other fields are allowed):

| Field | Rule |
|---|---|
| `id` | `ast` followed by digits, generated by the app. Do not invent your own format. |
| `type` | `MEMORY`, `DOCUMENT` or `SKILL` |
| `scope` | `GLOBAL` or `WORKSPACE` |
| `workspace` | Required for `WORKSPACE`, forbidden for `GLOBAL`; must be a registered project |
| `title` | Non-empty |
| `summary` | Non-empty; should agree with the conclusion in the body |

A file is skipped — and reported in **System status** — when:

- its front matter is invalid, or its scope, project or type does not match the folder it is in;
- another file uses the same `id`;
- it is a symlink, a directory, or not a Markdown file;
- it refers to a project that is not registered.

Each file's identity is the SHA-256 of its exact bytes. Line endings, Unicode and YAML order are not normalised, so any byte change counts as a change.

## Writing good precedents

A precedent should make sense on its own, months later, to an agent that has never seen the original conversation. It should answer:

- **What is the conclusion?** Say whether it is a rule, a historical observation, or how something was implemented at a certain point.
- **When does it apply?** Project, environment, preconditions — and the main cases where it does not.
- **Why?** The reasons and the cost of the choice. Do not invent alternatives that were never considered.
- **What supports it?** What was actually verified, how, and what was not. Keep only the smallest excerpt that lets someone check the judgment; label excerpts, paraphrases, inferences and examples as such.
- **What must be re-checked before reusing it?** The few facts that decide whether it still holds.

A quick test: hide every link, path and line number in the text. If the conclusion, conditions and reasons still make sense, the precedent is self-contained. If all that is left is "see file X", fill in the meaning.

Suggested body structure for a `MEMORY`:

```markdown
## Conclusion and when it applies
## Reasons and trade-offs
## Evidence and verification
## Re-check before reuse
```

Merge or drop sections that do not apply. `SKILL` bodies follow trigger → prerequisites → steps → verification → stop conditions. `DOCUMENT` bodies use whatever sections suit the material.

## Editing files directly

You can edit files under `assets/` with any editor; changes are picked up automatically. Direct edits are not recorded as reviewed versions, so the Hub's diff view will report that the file no longer matches the last approved version. For changes you want reviewed and versioned, ask an agent to prepare a revision, or edit the candidate in the Hub.
